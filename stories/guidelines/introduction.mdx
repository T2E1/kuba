# Kuba

Web Components, the browser itself as the dataflow layer, and no promise
to reinvent what the platform already solves.

Nobody needs many tools to build an interface that _works_. Building one
that still works two years from now, with someone else maintaining the
code, is the real challenge — and that comes from explicit conventions,
not individual talent.

When the domain is clear — which elements exist, how they talk to each
other, where state lives — the number of decisions each developer has to
make alone drops sharply. Changes become surgical: you know exactly which
file to touch and what to expect from the edit.

> Kuba doesn't abstract the DOM away — it trusts it.

This documentation is the single source of truth for how Kuba behaves and
why it was designed this way. Like any system of conventions, it only
pays off when it's followed — and following it well is the result of
keeping this reference alive, not writing it once and forgetting it.

## Goals

### Close the gap between two worlds

Component frameworks (React, Vue, Angular) solve client-side dataflow at
the cost of an entire runtime. htmx solves simplicity by handing HTML
back to the server, but has no local dataflow. Kuba exists to occupy that
exact middle ground: instant reactivity between elements, without giving
up HTML as the source of the application — see **Guidelines/Design
Principles** for the full reasoning.

### Support learning

Every package under `packages/` documents a decision: why `Echo`
overrides `dispatchEvent`, why `<kb-input>` delegates to the Constraint
Validation API instead of reimplementing it, why there is no central
"store". Making that reasoning explicit matters as much as the code
itself.

### Be a foundation for real products

Kuba is not a framework that dictates one way of working — it's a
reference to be studied, understood, and adapted to the reality of each
product. The guarantees about behavior and structure come from the
principles, not from a rigid API that must be obeyed to the letter.

## What we're aiming for

**Lower the cost of change.** By leaning on native browser APIs —
events, `CustomEvent`, `ElementInternals`, the Constraint Validation API
— each element evolves in isolation, with no cascade of edits across
other layers.

**Save time.** Small components, each with a single responsibility, mean
less accumulated technical debt and faster updates to apply.

**Build a culture of living documentation.** Every public package has a
`types.d.ts` as its contract and, when visual, a Storybook story that
also doubles as an interaction test. Documenting isn't a final step —
it's part of the definition of done.
