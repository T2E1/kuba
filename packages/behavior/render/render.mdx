# Render

`<kb-render>` renders its shadow DOM content by interpolating a template
against arbitrary data, supplied via `render()`, and emptied again via
`clear()`. It's also an Echo host: its `on` attribute (or a `<kb-on>`
child) can wire either method to another element's event — e.g.
re-rendering whenever a data source dispatches `change`, or clearing on
an `error` — so updates happen declaratively, without a manual event
listener or a framework's reactivity system.

## When to use

- Displaying a **list or grid of records** whose shape stays the same but
  whose data changes — one `{name} — {age}`-style template, re-rendered
  against a new data array each time.
- **Wiring rendering to an event** instead of writing a manual
  `addEventListener` + DOM update — see `WiredToAFetch` below.

## When not to use

- **Static content that never changes after first render** — plain HTML
  has no need for `<kb-render>`'s template/interpolation machinery.
- **Content requiring conditional branching or nested structure beyond
  simple `{path.to.value}` interpolation** — `<kb-render>`'s template
  engine only substitutes placeholders; it has no `if`/loop syntax of its
  own beyond "one interpolation per array entry."

## Composition

- **Can contain**: a single `<template>` child (read once via
  `this.querySelector('template')` when the `template` attribute is
  unset), and/or one or more `<kb-on>` children to wire additional
  subscriptions beyond the single `on` attribute — see
  `Foundations/Dataflow`. The template's `innerHTML` is used verbatim, or
  — if it has no HTML text, only child elements — the concatenated
  `outerHTML` of those children.
- **Can be a child of**: anything — `kb-render` has no parent
  requirement.

## Layout

`layout` controls how slotted/rendered content is arranged, not its
styling:

| Layout | Arrangement | Use for |
|---|---|---|
| `list` (default) | Single flex column | A vertical list of records, one per line. |
| `grid` | Two-column grid | Records better scanned side by side (e.g. paired name/value entries). |

## Template resolution

- Set `template="some-id"` to reference a `<template>` declared elsewhere
  in the document — resolved once (via `document.querySelector('#some-id')`)
  and cached, useful when the same template is shared across multiple
  `<kb-render>` instances.
- Leave `template` unset to nest the `<template>` directly as a child —
  the common case, and the one shown in the playground above.

## Data and re-rendering

- `render(data)` accepts a single item or an array; a single value is
  coerced into a one-item list, so the same interpolation logic handles
  one or many entries, concatenated in order.
- Calling `render()` before the host has completed its initial paint is a
  silent no-op — always call it after the element is connected to the
  DOM (e.g. in response to an event, not synchronously at module load).
- Prefer wiring `render()` to a publisher's event (via `on`/`<kb-on>`)
  over calling it manually whenever possible — it keeps the update
  declarative and colocated with the markup instead of scattered in page
  script.
- `clear()` empties the rendered `textContent` without touching the
  template, so a later `render()` call still has a template to
  interpolate against. It's the natural counterpart to wire to an
  error/empty event — e.g. `<kb-on value="api/error:method/clear">` next
  to `<kb-on value="api/ok:method/render">`, as shown in the playground
  above, so a failed request clears stale results instead of leaving them
  on screen.

## Do's and don'ts

| Do | Don't |
|---|---|
| Nest a single `<template>` child for the common case | Set `template` to reference an external node when a direct child would do |
| Wire `render()` to a publisher's event via `on`/`<kb-on>` | Call `render()` manually from a listener you wrote yourself when `on` already covers it |
| Use `layout="grid"` for paired/scannable entries | Use `grid` for long free-form text that doesn't benefit from column alignment |
| Call `render()` only after the element is connected | Call `render()` synchronously right after creating the element — it's a silent no-op before first paint |
