# Input

An input is a single-line text field that behaves like a native one from
the form's point of view: it wraps a real `<input>` in its shadow DOM and
reports its value and validity to the owning `<form>` through
`ElementInternals`. It's form-associated, so it submits without a hidden
field or a manual `FormData` step.

## When to use

- **Any single-line value** — email, name, quantity, date — inside a
  `<form>` or a `<kb-form>`.
- **Fields that must validate natively** — `required`, `pattern`, `min`,
  `max`, `minlength`, `maxlength` and `type` are all forwarded to the
  inner input, so the browser does the checking.
- **Fields that publish changes** — the element dispatches `changed` on
  every value change, which Echo can wire to another element without a
  listener.

## When not to use

- **Multi-line text** — use `<kb-textarea>`, which auto-resizes to its
  content.
- **A file** — use `<kb-fileupload>`, which previews the selection and
  encodes it for submission.
- **Choosing among known options** — a text field that expects one of
  five values should be a select or a radio group; `pattern` validation is
  not a substitute for a constrained control.

## Composition

- **Can contain**: content for its three named slots — `label`, `helper`
  and `validity` (see `component.js`). Anything unslotted is dropped.
  `<kb-label>`, `<kb-helper>` and `<kb-validity>` all assign themselves to
  the matching slot on connect, so nesting them is the whole setup — more
  than one `<kb-validity>` can share the slot.
- **Can be a child of**: a `<form>`, a `<kb-form>`'s template, or nothing
  at all — the element works standalone, it just has no form to submit to.
  Inside a `<kb-stack direction="column">` it takes the full width of the
  column.

```html
<kb-input name="email" type="email" required>
  <kb-label>Email</kb-label>
  <kb-helper>We'll never share it.</kb-helper>
  <kb-validity state="valueMissing">
    This field is required.
  </kb-validity>
  <kb-validity state="typeMismatch">
    Enter a valid email address.
  </kb-validity>
</kb-input>
```

## Validation

Constraints are declared as attributes and evaluated by the browser; the
result is mirrored onto the host as an `invalid` custom state, which is
what the styling and `<kb-validity>` react to.

- Set `required`, `pattern`, `min`/`max`, `minlength`/`maxlength` and
  `type` on the element — they reach the inner input unchanged.
- Read the outcome through `checkValidity()`, `reportValidity()`,
  `validity` and `validationMessage`, the same API a native input exposes.
- While the host is in the `invalid` state, the `helper` slot is hidden
  (see `style.js`) so the error message replaces the hint instead of
  stacking under it. That's why a hint and its error should not repeat
  each other.
- Give each failure its own `<kb-validity state="...">`. A single generic
  message forces the user to guess which rule they broke.

`reset()` clears the value and the invalid state, and dispatches `reset` —
`<kb-form>`'s reset flows through to every field this way.

## Events

`changed` fires on every value change, carrying the new value as
`event.detail`. It's the hook for both listeners and Echo arcs:

```html
<kb-input name="query"></kb-input>
<kb-fetch url="/search?q={}">
  <kb-on value="query/changed:method/get"></kb-on>
</kb-fetch>
```

Note the event name: it's `changed`, not the native `change`, and it fires
per keystroke rather than on blur. Debounce it (`|debounce=300` in an arc)
before using it to drive a request.

## Styling

The field's surface is exposed as `--input-*` custom properties, which
inherit through the shadow boundary — set them on the element (or any
ancestor) rather than reaching into its shadow DOM.

| Custom property | Default | Controls |
|---|---|---|
| `--input-color-background` | `var(--color-master-lightest)` | Field background. |
| `--input-color-background_disabled` | `var(--color-master-lighter)` | Background when disabled or read-only. |
| `--input-color-border` | `var(--color-master-light)` | Border in the resting state. |
| `--input-color-focus` | `var(--color-primary)` | Border on focus. |
| `--input-color-invalid` | `var(--color-danger)` | Border while the `invalid` state is set. |
| `--input-color-text` | `var(--color-master-dark)` | Typed text. |
| `--input-color-text_disabled` | `var(--color-master)` | Text when disabled or read-only. |
| `--input-color-placeholder` | `var(--color-master)` | Placeholder text. |
| `--input-font-family` | `var(--font-family-base)` | Type family. |
| `--input-font-size` | `var(--font-size-xxs)` (14px) | Type size. |
| `--input-size-height` | `40px` | Field height. |
| `--input-space-inset` | `var(--spacing_inset-nano) var(--spacing_inset-xs)` | Field padding — accepts the full CSS shorthand. |
| `--input-border-radius` | `var(--border-radius-sm)` | Corner rounding. |
| `--input-space-gap` | `var(--spacing-nano)` | Gap between label, field, and helper/validity. |

Width is an attribute (`width`, from the `Width` mixin), not a custom
property — set it there rather than in CSS.

```css
/* A larger field for a single-question step */
kb-input.hero {
  --input-size-height: 56px;
  --input-font-size: var(--font-size-sm);
}
```

## States and accessibility

- The element uses the `Hidden` mixin: `hidden` adds the `hidden` custom
  state and `display: none`, removing the field from layout and from the
  accessibility tree.
- `invalid` is a custom state set from the Constraint Validation API, not
  an attribute you set. Style it with `:state(invalid)`, don't try to
  force it.
- The inner `<label for>` points at the inner input using the element's
  `id` (falling back to `name`), so slotted label content is properly
  associated — but only when `id` or `name` is set. A field with neither
  has an unlabelled input.
- `disabled` removes the field from submission entirely; `readonly` keeps
  it in the `FormData`. Choose by whether the value should still be sent.
- The error message replaces the helper text visually. If the hint carries
  a requirement the user still needs while fixing the error, repeat it in
  the `<kb-validity>` message.

## Do's and don'ts

| Do | Don't |
|---|---|
| Set `name` (or `id`) so the label associates and the value submits | Rely on a visible `<kb-label>` alone to name the field |
| Give each constraint its own `<kb-validity state="...">` | Ship one generic "Invalid input" for every failure |
| Debounce `changed` before driving a request | Fire a request per keystroke straight from the event |
| Use `type` and `pattern` so the browser validates | Re-implement format checking in script and set the state by hand |
