# Navegación declarativa

Navegar sin escribir `history.pushState` en ninguna parte: un botón publica
`clicked`, y un `<kb-redirect>` se suscribe. El botón nunca aprende adónde lleva,
que es lo que lo mantiene reutilizable.

```html
<kb-button id="to-profile">Ver perfil</kb-button>
<kb-redirect href="/profile" on="#to-profile/clicked:method/go"></kb-redirect>
```

?> No hay preview en vivo en esta página. Cada ejemplo llamaría a `pushState` y
cambiaría la URL de la propia documentación.

## Por qué el botón no conoce el destino

La alternativa que elige la mayoría de las bases de código mete la navegación
dentro del control:

```html
<!-- No hagas esto: el botón ahora conoce el enrutado -->
<kb-button onclick="location.href = '/profile'">Ver perfil</kb-button>
```

Ese botón no puede reutilizarse donde el destino sea otro, y no puede probarse
sin un router. Dividirlo en dos mantiene a cada elemento responsable de una cosa:
el botón informa que fue pulsado, el redirect decide qué significa eso.

## Segmentos dinámicos

Un solo redirect sirve una lista entera cuando el destino tiene un placeholder
rellenado por el payload del evento:

```html
<kb-render>
  <kb-on value="users/changed:method/render"></kb-on>
  <template>
    <kb-card value="{id}">
      <kb-text size="xxs">{name}</kb-text>
    </kb-card>
  </template>
</kb-render>

<kb-redirect href="/user/{}" on="kb-card/clicked:method/go"></kb-redirect>
```

Dos cosas lo hacen posible:

- El `value="\{id\}"` de cada tarjeta se interpola por registro, así que cada una
  publica su propio id como payload del `clicked`.
- El origen del arco es el **nombre de etiqueta** `kb-card`, que coincide con
  todas las tarjetas de la página en lugar de con una por id — así las
  renderizadas después también quedan cubiertas.

`\{\}` en el `href` es el payload completo. Para un payload en objeto, nombra la
ruta: `href="/user/\{id\}/settings"`.

## Rutas con nombre

Cuando el router es dueño de las formas de URL, usa `route` en vez de `href` y
deja que `urlFor` lo resuelva:

```js
import router from '@t2e1/kuba/router'

router('/user/:id', function showUser() {
  // renderiza la página del usuario
})
```

```html
<kb-redirect route="showUser" on="kb-card/clicked:method/go"></kb-redirect>
```

La ruta se encuentra por el **nombre de la función de página** — `showUser` — así
que no puede ser una arrow anónima. Nombrarla es lo que la hace direccionable.

!> Definir `route` y `href` a la vez no da un fallback. Con `route` definido,
`href` nunca se usa.

## Reaccionar a la navegación

`go()` llama a `history.pushState`, que emite un evento `pushstate` en `window`.
El router lo escucha y ejecuta la ruta correspondiente, así que la página se
actualiza sin recarga:

```js
import router, { params } from '@t2e1/kuba/router'

router('/user/:id', function showUser() {
  document.querySelector('kb-fetch[name="user"]').get({ id: params.id })
})
```

La cadena de principio a fin: clic en la tarjeta → el redirect navega → el router
coincide → el callback de la ruta solicita → el fetch publica `succeeded` → un
renderizador se suscribe. Dos de esos cinco pasos son JavaScript, y ambos son
sobre enrutado, no sobre conexión.

## Cuándo usar un enlace de verdad

Este patrón renuncia a cosas que un `<a href>` da gratis:

- el destino al pasar el ratón, y en la barra de estado
- abrir en pestaña nueva, copiar la dirección, guardar en marcadores
- ser anunciado como enlace por la tecnología asistiva
- funcionar antes de que cargue el JavaScript

**Cuando la cosa genuinamente *es* un enlace, usa un `<a>`.** Recurre a
`<kb-redirect>` cuando la navegación es *consecuencia* de una acción — un guardar
que vuelve a una lista, una selección que abre un detalle — y no la acción en sí.
